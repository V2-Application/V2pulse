# Deploying V2Pulse on DataCenter (192.168.151.27)

V2Pulse runs as three Windows services on the DataCenter box, beside the Report Portal (:8874):

| Service | What | Port |
| --- | --- | --- |
| `V2PulseDB` | Dedicated PostgreSQL 16 instance, data in `D:\V2PulseData\pgdata` | 127.0.0.1:5435 (not reachable from the LAN) |
| `V2Pulse` | Web app + API (uvicorn, 2 workers) | 8875 |
| `V2PulseWorker` | Background jobs (HR sync, snapshots, Control Tower, portal checks, log partitions) | — |

Code lives in `D:\Mahesh\Python\v2pulse` (`\\DataCenter.v2rd.com\Python\v2pulse`). The existing
Postgres instances on 5432, 5433 and 5434 (PostgreSQL 15/17/18) are not touched.

## One-time install (over RDP, as Administrator)

1. **Settings.** Copy `deploy\env.bat.example` to `D:\Mahesh\Python\v2pulse\env.bat` and fill it in.
   Postgres passwords: 24+ characters, letters and digits only (they go into connection URLs and batch files).
2. **Snowflake, Part B.** Someone with ACCOUNTADMIN runs Part B of `deploy\snowflake_setup.sql`
   (creates `PULSE_SVC` and `PULSE_SVC_ROLE`; uses the existing `COMPUTE_WH`, no new warehouse).
   Part A (the `V2RETAIL.PULSE` views) is already applied.
3. `deploy\setup.bat` — venv, packages, and the `PULSE_SVC` key pair (generated on the server; the
   private key never leaves it). It prints an `alter user PULSE_SVC set rsa_public_key = ...` line:
   run that in Snowflake as ACCOUNTADMIN.
4. `deploy\install-postgres.bat` — creates the `V2PulseDB` service, roles, database, and applies migrations.
5. `deploy\install-services.bat` — installs and starts `V2Pulse` and `V2PulseWorker`, opens port 8875.
6. Open `http://DataCenter.v2rd.com:8875/healthz` → `{"ok": true, ...}`.

## Masters (Part C)

The Masters library reads one curated view per master in `V2RETAIL.PULSE`. Create or refresh them with
`deploy\snowflake_masters.sql` (as ACCOUNTADMIN or DATA_PLATFORM_ADMIN; safe to re-run). The file is generated
from `pulse/modules/masters_catalog.py`: `venv\Scripts\python.exe -m pulse.cli masters-sql > deploy\snowflake_masters.sql`.
Then run the `masters_profile` job (Admin › Jobs) to read row counts and columns. A master whose view is missing
shows "View missing" in Admin › Masters catalog and a clear message to users; nothing else breaks.

## Dynamic reports (Part D)

Dynamic (Power BI-style) reports query governed datasets, one curated view each in `V2RETAIL.PULSE`. Create or
refresh the views with `deploy\snowflake_bi.sql` (as ACCOUNTADMIN; safe to re-run), generated by
`venv\Scripts\python.exe -m pulse.cli bi-sql > deploy\snowflake_bi.sql`. Fields and measures are edited in
Admin › Datasets. Library reports need `reports.design` (administrators); personal reports need `reports.personal`.

## DFS reports replicated into Central

The 35 live DFS report definitions (`BRONZE.MIS_REPORT_DEF`, snapshotted to `pulse/modules/dfs_defs.json`) are
replicated as Central **dynamic reports** under categories **DFS — Store / RDC / DC** (Reports › Dynamic).
They run on one governed dataset, `dfs_sale`, a view `V2RETAIL.PULSE.V_BI_DFS_SALE` that joins the daily
sale fact (`BRONZE.DAY_WISE_ST_VAR_SALE`) to the article master and store dimension. The fact is additive
(no snapshot), so a period's figure is the sum of its days; each report defaults to the last 31 days and the
time hierarchy / Date slicer gives TD/MTD/QTR/YTD. Store scope applies. The view is in Part D / the combined
`V2Pulse_views_ONE_STATEMENT.sql`; re-run that in Snowsight as ACCOUNTADMIN to (re)create it. DFS reports are
excluded from `bi_prewarm` (heavy 100M-row joins); they cache on first open. To refresh the definitions,
re-snapshot `MIS_REPORT_DEF` into dfs_defs.json and redeploy.

## First sign-in

Until Microsoft sign-in is registered (below), the pilot uses break-glass passwords:

1. The worker's first HR sync (within a minute of start) loads all active employees and makes the
   codes in `PULSE_BOOTSTRAP_ADMINS` portal administrators with company scope.
2. On the server, set the first admin's password once:
   `venv\Scripts\python.exe -m pulse.cli set-password V23375`
3. Sign in at `http://DataCenter.v2rd.com:8875` with employee code + password. Then use
   Admin › Users to give pilot users roles and (where needed) passwords.

## Web address: http://v2pulse.v2retail.com

IIS site **V2Pulse** (app pool V2Pulse, no managed code) binds `http *:80` for host `v2pulse.v2retail.com` only and
proxies to the service with ARR + URL Rewrite (`deploy\iis-site\web.config`, same pattern as LoyaltyDash). env.bat sets
`PULSE_BASE_URL=http://v2pulse.v2retail.com` and `PULSE_TRUSTED_PROXIES=127.0.0.1/32,::1/128` so the logs keep each
person's real IP (ARR's `ip:port` X-Forwarded-For is handled). Internal DNS needs an A record
`v2pulse.v2retail.com -> 192.168.151.27`, like loyalty / karma / crm. Port 8875 keeps working directly.
For HTTPS add an `https *:443` binding for the same host with a valid `*.v2retail.com` certificate (the one on this
server expired on 4 Jun 2026), then set `PULSE_BASE_URL=https://v2pulse.v2retail.com` and `PULSE_COOKIE_SECURE=true`.

## V2 Parivar (HRMS) sign-in

Employees sign in with their existing **V2 Parivar employee code and password** — no password is set per
person in V2Pulse. At sign-in V2Pulse POSTs the code + password to the Parivar login API and reads only
whether they are valid; the password is never stored or logged. Access still comes only from the employee
record loaded by the hourly HR sync, so a valid Parivar account that is not an active V2Pulse employee
(left staff, service IDs) cannot get in. env.bat settings (confirmed against Parivar on 14 Oct 2026):

    set PULSE_PARIVAR_LOGIN_URL=https://v2parivar.v2retail.com:9987/api/Auth/loginnew
    set PULSE_PARIVAR_USER_FIELD=userName      (API field for the employee code)
    set PULSE_PARIVAR_PASS_FIELD=password
    set PULSE_PARIVAR_SUCCESS_FIELD=status     (response field that is true on success)
    set PULSE_PARIVAR_VERIFY_TLS=true          (the :9987 certificate validates)

Blank `PULSE_PARIVAR_LOGIN_URL` hides the provider. The break-glass employee-code+password (`local`) login
stays available for admins in case Parivar is down; set `PULSE_LOCAL_LOGIN_ENABLED=false` to turn it off.

## Microsoft (Entra ID) sign-in — needs IT

Entra accepts only **https** redirect addresses (except localhost), so this needs:

1. A DNS name for the server (e.g. `pulse.v2retail.com` → 192.168.151.27 on the internal DNS) and a
   certificate for it (PEM cert + key). Put their paths in `PULSE_TLS_CERT` / `PULSE_TLS_KEY`, set
   `PULSE_BASE_URL=https://pulse.v2retail.com:8875` and `PULSE_COOKIE_SECURE=true`.
2. An app registration in Entra: single tenant, Web platform, redirect URI
   `https://pulse.v2retail.com:8875/auth/entra/callback`, a client secret, optional claim `email`.
   Put tenant id, client id and secret into env.bat.
3. `deploy\update.bat`. The "Sign in with Microsoft" button appears. Accounts are matched to employees
   by email; staff whose HRMS email is missing or shared get linked in Admin › Users › Link email.

## Updating

From the laptop: `bash scripts/deploy_to_server.sh` (builds the web app, copies code to the share).
Then on the server, as Administrator: `deploy\update.bat` (packages, migrations, restart).

## Where to look

| Question | Where |
| --- | --- |
| Is it up? | `/healthz`; `logs\api.log`; Services console |
| Did a job run? | Admin › Jobs (history per job); `logs\worker.log` |
| Who did what / who viewed what? | Admin › Logs (actions; views & API calls; CSV export) |
| Is data fresh? | Data page (freshness contract per dataset) |

## Rollback

Stop `V2Pulse` and `V2PulseWorker`. The Report Portal on :8874 is unaffected and keeps running.
Database backups: `pgsql\bin\pg_dump.exe -h 127.0.0.1 -p 5435 -U pulse_owner -Fc pulse > D:\V2PulseData\backup\pulse-<date>.dump`
(schedule nightly; see the open items in the design doc).
